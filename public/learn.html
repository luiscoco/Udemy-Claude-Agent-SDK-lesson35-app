01

Compare prompt input types

Pass a string for a one-shot query or an AsyncIterable of SDKUserMessage objects for a long-lived interactive query. Both still produce an asynchronous output stream; input mode and output streaming are separate concepts.

02

Keep conversation context deliberately

One streaming Query naturally retains its session context. Independent string queries start separate sessions. An explicit resume session ID can continue a persisted string session; continue selects the latest matching session instead.

03

Bridge the UI with a bounded queue

A FIFO inbox wakes its waiting generator. This classroom host waits for each actual result before yielding the next queued message, making ordering visible and avoiding merged queued turns. Closing the queue releases idle waits.

04

Send an actual image follow-up

The SDK message carries text and a real base64 PNG block. Inspect the supplied architecture image, send it after the first result and compare the agent’s actual visual answer with the image.

05

Interrupt and control the live query

Use interrupt during an actual delayed Read, then continue the same Query. Await setPermissionMode acknowledgement before the next input. New chat starts a fresh Query and session; Finish closes the input queue.

06

Handle errors and choose the right lifetime

Drain a string query loop so an exception after error_max_turns is caught. A streaming query can remain alive after the cap result and accept a recovery message. One-shot work suits short-lived hosts; interactive queues need a process and explicit cleanup.
